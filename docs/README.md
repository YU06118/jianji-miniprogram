# 简记 · 文档中心

> 本目录是「简记」微信小程序的唯一文档源。所有阶段产出、验证报告、核查记录均按本规范组织。
> 最后整理：2026-11-26（阶段 0～7 文档规范化）

## 1 目录与阶段语义

| 阶段 | 目录 | 主题 | 定位 |
|---|---|---|---|
| 0 | `阶段0/` | 技术方案 | 需求基线、技术选型、数据模型、动效与降级、Q1～Q8 待确认项 |
| 1 | `阶段1/` | 骨架 | 工程配置 / token / 玻璃组件 / 存储与工具 / 类型 / 单测 |
| 2 | `阶段2/` | 记账与列表 | 记一笔、账单列表、分类管理、搜索详情 |
| 3 | `阶段3/` | 统计与预算 | 环形图 / 柱图 / 预算进度 / 数字滚动 |
| 4 | `阶段4/` | 数据与同步 | 导出导入 / 隐私合规 / 云同步可插拔 / 云函数 |
| 5 | `阶段5/` | 走查交付 | 真机清单 / 静态走查 / 用户手册 / 最终回归 |
| 6 | `阶段6/` | Q 系列专项核查 | 阶段 0 §8 待确认项 Q6/Q7/Q8 的落地核查与补全 |
| 7 | `阶段7/` | 质量复盘与最终交付 | 全项目质量总结、缺陷分布、根因分类、改进建议、交付结论 |

**阶段编号约定**：
- 阶段 0～5 是开发阶段，按阶段门推进，每阶段有「验证报告」（开发方自验）。
- 阶段 6 的「Q 系列」不是新开发阶段，而是阶段 0 §8 待确认决策（Q6 记一笔形态、Q7 预设分类、Q8 验收口径）的专项核查——因涉及跨阶段验证，独立成段。
- 阶段 7 是项目收尾，汇总前 6 阶段的全部检查结论，输出质量复盘与交付判定。

## 2 文档命名规范

```
阶段N/
├── 阶段N-技术方案.md        # 仅阶段 0：需求与技术基线
├── 阶段N-验证报告.md        # 开发方自验：本批改动 + 自动化结果 + 已知限制
├── 阶段N-代码检查报告.md    # 独立检查：需求对照 + 独立复验 + 缺陷判定 + 验收结论
├── 阶段N-缺陷修复记录.md    # 检查发现问题后的修复说明与回归（有则建）
└── 阶段N-<专项>.md          # 阶段专属文档（如部署说明、真机清单）

阶段6/Q<编号>-<主题>.md      # Q 系列核查按 Q 编号命名
```

**一级标题格式**：
- 阶段文档：`# 简记 · 阶段 N · 文档类型`（N 用阿拉伯数字，阶段号与类型用 `·` 分隔）
  - ✅ `# 简记 · 阶段 1 · 验证报告`
  - ❌ `# 简记 · 阶段一验证报告`（中文数字无分隔）、`# 简记 · 云同步说明（阶段 4）`（阶段号后置）、`# 简记 · 代码一致性检查报告`（无阶段号）
- 阶段 6 的 Q 系列：`# 简记 · Q<编号> · 主题`（Q 编号即身份，省略阶段前缀）
  - ✅ `# 简记 · Q6 · 记一笔形态核查与补全`
- 根目录通用文档：`# 简记 · 文档名`（不属任何阶段，无阶段号）
  - ✅ `# 简记 · 用户操作手册`、`# 简记 · 项目交付总览`、`# 简记 · 文档中心`

**元信息块**（标题下紧跟 `>` 引用块）：触发来源 / 检查或编写时间 / 判定基线 / 结论。

**验收结论用词统一**：`通过` / `附条件通过（说明条件）` / `不通过（说明阻断项）`。避免"基本符合""大致可用"等模糊表述。

## 4 文档维护约定

1. **检查报告保留历史**：每轮复检追加新章节（如「§8 复检结论」），不覆盖旧结论；结论变更时明确标注"由 X 更新为 Y"。
2. **缺陷结构化**：位置、复现步骤、实际/期望结果、判定依据、影响、修复建议六要素齐全；证据不足时标注"待真机确认"，不断言根因。
3. **注入验证要还原**：为验证单测/门禁而临时注入的代码（如改名、注入 `any`）跑完必须还原，并在报告中写明"已还原"。
4. **引用路径校验**：移动或重命名文档后，全局搜索旧路径并更新；本目录所有相对链接应指向存在的文件。
5. **规范变更**：本文件自身变更时更新顶部"最后整理"日期。
