## 2 BUG-01：软删除墓碑丢失（P0）

### 独立复现（修复前）

我未直接采信检查报告，而是先写了一次性复现测试实跑，结果与报告一致且更严重：

```
创建 A、B → deleteRecord(A) → deleteRecord(B)
存储实际 = [{"id":"rec-mw...","note":"B","isDeleted":true}]  // 只剩 B
期望 = 两条 isDeleted:true
Received length: 1   ❌ FAIL
```

### 根因（比报告描述更广）

报告指出 `deleteRecord` 的问题。实际核查发现**三个写操作全部中招**：

| 函数 | 原代码 | 后果 |
|---|---|---|
| `createRecord` | `loadRecords()`（已过滤墓碑）→ `saveRecords([record, ...all])` | 新增一笔即抹掉所有墓碑 |
| `updateRecord` | `loadRecords()` → `saveRecords(all)` | 编辑一笔即抹掉所有墓碑 |
| `deleteRecord` | `loadRecords()` → 标记 → `saveRecords(all)` | 第二次删除抹掉第一次的墓碑 |

分类服务 `createAccount` / `updateAccount` / `deleteAccount` / `reorderAccounts` 同样基于 `loadAccounts()`（已过滤），存在相同缺陷。

**一句话根因**：写操作用了「读展示数据（过滤墓碑）→ 整体覆盖写回」的模式，展示层过滤语义被误用到写入路径。

### 修复方案

在 storage 层区分「读全量」与「读活跃」两个原语：

- 新增 `readAllRecords()` / `readAllAccounts()`：返回含墓碑的全量数组，**仅供写操作与同步**。
- 保留 `loadRecords()` / `loadAccounts()`：过滤墓碑，**仅供展示层**。
- 所有写操作（record 与 category 共 7 个函数）改为基于全量数组。
- 附带修正：
  - `deleteRecord` / `deleteAccount` 增加幂等保护，重复删除返回 `false`，不制造重复墓碑。
  - `updateRecord` / `updateAccount` 拒绝编辑墓碑。
  - `createAccount` 的 `sortOrder` 改用活跃计数，避免墓碑导致跳号。
  - `reorderAccounts` 墓碑不参与排序但保留。
  - `ensurePresetAccounts` 在极端情况（活跃分类为 0）初始化预设时追加墓碑而非覆盖。

### 回归用例（永久）

`record.service.test.ts` 新增 3 条：
1. 连续删除两条 → 两条墓碑都在
2. 删除后再新增/编辑 → 既有墓碑不丢
3. 重复删除同一条 → 幂等，仅一条墓碑

`category.service.test.ts` 新增 1 条：连续删除两条自定义分类 → 两条墓碑都在，重复删除幂等。

## 3 BUG-02：编辑回填浮点除法（P2）

- **修复前**：`keypadFromString(String(record.amountInCents / 100))`
- **修复后**：`keypadFromString(formatYuan(record.amountInCents))`
- `formatYuan` 用整除 + 取余实现，全程整数运算，符合 §2.3 硬约束。
- **回归用例**：1234 → "12.34"、888000 → "8880.00"、1 分 → "0.01" 且 round-trip 回分无损。

## 4 RISK-02：rAF 防御式回退（P1）

- **修复前**：仅 `declare const requestAnimationFrame`，若某端运行时无此全局，首帧即 `ReferenceError`。
- **修复后**：
  ```ts
  const raf = typeof requestAnimationFrame === 'function'
    ? (cb) => { requestAnimationFrame(cb); }
    : (cb) => { setTimeout(cb, 16); };
  ```
- 运行时检测，缺失回退 `setTimeout(16ms)`，彻底规避双端差异。阶段 5 真机仍列为必测项。
