## 4 缺陷清单

### BUG-01 · 软删除墓碑丢失（P0，已复现，阻断进入阶段 3）

- **位置**：`services/record.service.ts` `deleteRecord()`（75～83 行）+ `utils/storage.ts` `loadRecords()`（76～78 行）/ `saveRecords()`（80～82 行）
- **根因链**：
  1. `loadRecords()` 用 `.filter(r => !r.isDeleted)` 过滤掉已有墓碑，只返回活跃记录
  2. `deleteRecord()` 在过滤后的数组上把目标标记为 `isDeleted:true`
  3. `saveRecords()` 用这个**残缺数组整体覆盖**存储 → 之前的墓碑被抹掉
- **复现证据**（一次性测试，已删除）：
  ```
  创建 A、B → deleteRecord(A) → deleteRecord(B)
  存储实际 = [{"id":"rec-mw...","isDeleted":true}]   // 只剩 B，A 的墓碑没了
  期望 = 两条 isDeleted:true
  expect(stored.filter(r=>r.isDeleted)).toHaveLength(2)
  → Received length: 1  ❌ FAIL
  ```
- **实际结果**：第二次删除时，先前所有墓碑永久丢失
- **期望结果**：所有墓碑保留（方案 §2.5「软删除用 isDeleted 墓碑同步」、§6.2「软删除 + updatedAt，导出保留标记」）
- **影响**：阶段 4 开启云同步后，远端仍存在的已删记录按 `updatedAt` 合并会被判为新数据**复活**；本地导出数据亦丢失删除痕迹
- **为何单测没抓到**：`record.service.test.ts` 的「软删除后查询不到」只删了**一条**并断言长度 1，单次删除墓碑当然留得住；缺失「连续删除两条」场景
- **修复建议**：
  - 方案 A（推荐）：`saveRecords()` 改为合并写回——读取磁盘全量，用入参替换活跃条目，同时保留原 `isDeleted:true` 条目
  - 方案 B：新增 `markRecordDeleted(id)` 直接读写全量数组，`deleteRecord` 不走 `loadRecords()`
  - 两者都要补「连续删除 N 条 → N 条墓碑都在」的单测

### BUG-02 · 编辑态金额回填使用浮点除法（P2，设计红线偏离）

- **位置**：`pages/record-editor/index.ts` 第 55 行
  ```ts
  const keypad = record ? keypadFromString(String(record.amountInCents / 100)) : EMPTY_KEYPAD;
  ```
- **问题**：方案 §2.3 规定「金额禁止浮点参与运算」。此处用 `amountInCents / 100` 得浮点数，经 `String()` 转字符串再回填键盘。虽然多数两位整数分值能被 JS 浮点精确表达（如 1234/100 = 12.34），但该写法违反硬约束，且对特殊值（极大金额、科学计数法边界）存在回填失真风险
- **期望结果**：用纯整数路径回填，如 `formatYuan(record.amountInCents)` 得到 `"12.34"` 再传给 `keypadFromString`
- **修复建议**：`keypadFromString(formatYuan(record.amountInCents))`，并补一条「整数分→键盘显示」单测（如 1234 → "12.34"、888000 → "8880.00"）

### RISK-02 · number-roller 的 requestAnimationFrame 可用性未证实（P1 风险，真机验证项）

- **位置**：`components/number-roller/index.ts` 第 9 行 `declare const requestAnimationFrame: ...`
- **现状**：阶段 2 验证报告称「小程序运行时有全局 requestAnimationFrame，类型包未声明，补 declare 即可」
- **核查结果**：**证据不足，不断言根因**。公开资料互相矛盾——有开发者实测「Android 小程序有、iOS 小程序没有」（gitmemories 案例），另有文章称逻辑层做了适配（bbccb 文章）；微信官方《JavaScript 支持情况》文档未明确背书 rAF 全局可用性
- **风险**：`declare const` 只骗过 TypeScript，不改变运行时。若某端真无 rAF，数字滚动首帧即 ReferenceError
- **建议**：
  - 阶段 5 真机走查把 iPhone + Android 双端的 NumberRoller 列为必测项
  - 或改为防御式写法：`const raf = typeof requestAnimationFrame === 'function' ? requestAnimationFrame : (cb) => setTimeout(cb, 16) as unknown as number`，彻底规避平台差异

### OBS-6 · 图片压缩 5 轮后仍超限（已知限制，接受）

- `utils/image.ts` `compressToLimit` 循环最多 5 轮，极少数超大图可能仍 >200 KB；实现如实返回原压缩结果、不静默丢弃，与阶段 2 验证报告 §5 一致。属可接受限制，阶段 5 真机抽查。

### OBS-7 · 分类色值硬编码（P2，规范偏差）

- `services/category.service.ts` 第 17～24、71 行硬编码 `#8B7BE8` 等 8 个预设色值；`utils/migration.ts` 第 30 行同样。与方案 §5「theme.wxss 唯一色值来源」字面冲突。建议在 WXML 层用 CSS 变量或抽 `utils/tokens.ts` 统一。
