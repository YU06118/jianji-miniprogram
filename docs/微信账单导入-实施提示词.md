## 2. 任务 A：微信账单导入

### A1. 取数路径（只做这两条，第三条明确不做）

1. **聊天文件**：`wx.chooseMessageFile({ count:1, type:'file', extension:['csv'] })`。用户在微信里把账单 csv 发到「文件传输助手」，再从聊天记录里选。
2. **粘贴兜底**：提供"粘贴账单内容"入口，读剪贴板文本走同一解析器。用于无法选文件的机型/场景。

**不做，并在代码注释里写明原因**：微信导出的是**带密码的 zip**，小程序侧解压需引入解压库且要处理 AES，体积与失败率都不可接受；xlsx 需内联 SheetJS，包体代价高于收益；截图 OCR 准确率不足，会产生错账。**一期只吃已解压的 .csv。**

### A2. 解析口径（每一条都是实测踩出来的，不得简化）

1. **表头定位**：微信个人对账账单表头之上有 10–16 行说明，其中第 3 行是 `起始时间：[...] 终止时间：[...]`。**必须要求多列同时命中才认作表头**——至少同时出现「交易时间 / 交易对方或商户 / 金额 / 收-支」四类中的三类。单列模糊匹配会把说明行当表头，结果一条都解析不出来（这是原实现失效的直接原因）。
2. **切分**：不能用 `split(',')`。微信「商品」「备注」字段可能含逗号（`"女装,外套"`），必须做引号感知切分，支持 `""` 转义。
3. **金额**：原文形如 `¥65.00`。去 `¥`、千分位逗号、空格后转数字，再 `Math.round(x*100)` 转分。**全程不在分之外做浮点比较。**
4. **方向**：以「收/支」列为准，该列取 `收入` 为收、`支出` 为支。**不要用「交易类型」列判方向**——它在第 2 列，会被"从左找第一个含'类型'的列"这类写法抢先命中，导致转账收款、红包收入全部被记成支出。
5. **中性交易**：「收/支」为 `/`、`-`、`—`，或值为「不计收支」（零钱充值、提现、信用卡还款、理财存取）→ **不计入收支，也不写库**，只计数。
6. **退款**：`当前状态` 含「已全额退款」→ 该笔不计；含「已退款(¥x)」→ 按 `原金额 − x` 计净额，净额 ≤0 则不计。
7. **日期**：`交易时间` 只取 `YYYY-MM-DD`，不要用 `new Date(...).toISOString()`，东八区会跨日偏移。
8. **脏行**：汇总行（`共 N 笔记录` / `收入：…` / `支出：…`）与分隔线必须靠"日期格式不匹配即丢弃"排除，不要依赖行号。

### A3. 分类映射

- 新增 `services/wechat-import.service.ts`，内含单一映射表：微信的「交易类型 / 商品 / 交易对方」关键词 → 现有 `Account._id`。
- 顺序：先精确命中预设分类关键词，再模糊包含，都未命中落到「其他」分类。
- 映射表必须是**纯数据 + 纯函数**，可被单测直接喂样例断言；不得散落在页面里。
- 复用 `category.service.ts` 已有的分类清单与排序，不新增分类体系。

### A4. 去重与幂等（核心正确性要求）

微信导出的是**全量**，用户每月都会重导同一批，所以：

1. 优先用「交易单号」判重：账本内已有同单号即跳过。
2. 无单号时（粘贴场景可能丢列），按 `日期+金额+商户+分类` 的**出现次数对齐**：账本里已有 1 条就跳过第 1 条、放行第 2 条。
3. **禁止**只用 `日期+金额+商户` 做存在性判断——同一天同一食堂两笔 15 元是真实消费，不能被吞。
4. 导入是**合并**，不是覆盖。这与现有 JSON「覆盖导入」是两种语义，UI 文案与确认弹窗必须区分清楚，绝不能共用"将覆盖当前全部数据"的说法。

### A5. 写库与回滚

流程固定为：**选文件 → 解析 → 预览（不写库）→ 用户确认 → 批量写入 → 失败整体回滚**。

- 解析结果先在内存里算成 `{ 新增, 跳过, 中性, 退款, 错误行 }`，用 `glass-sheet` 展示预览。
- 确认后才 `saveRecords`；写入前备份当前 records，任一异常回滚到导入前状态（复用 `data-io.service.ts` 的回滚写法）。
- 导入完成后刷新 `data-manage` 的统计数字，`wx.showToast` 只报一行结果，不再弹 modal 复述。

### A6. 结果呈现（用布局表达，不写解释段）

预览面板只允许三层信息，全部靠结构与数字说话：

```
新增        37
跳过重复     12
不计入        4
```

- 上方标题只写「微信账单」+ 账单覆盖的月份区间（`2026-10-01 → 2026-10-31`），不写"本功能用于…"。
- 「不计入」旁不写解释；点它才展开三项小字：中性交易 / 已退款 / 无法识别行（最多各一行，带数字）。
- 主按钮唯一：`导入 37 笔`（数字进按钮文案，用户点之前就知道结果）。

### A7. 失败文案（每种一句，≤20 字，不带感叹号）

| 情形 | 文案 |
|---|---|
| 未选文件 | 未选择文件 |
| 表头识别失败 | 不像微信账单，检查是否选错文件 |
| 无可导入记录 | 这批都已记过 |
| 解析异常 | 解析中断，未写入任何数据 |
| 写入失败 | 写入失败，已回滚 |

## 3. 任务 B：设计语言复查

### B1. 唯一判据

**删掉这段文字之后，用户是否仍能判断"点这里会发生什么、结果是什么"？** 能，就删。

按此判据，现有 `data-manage` 页有三处在删了也不影响判断的辅助文案，必须处理：

1. `dm-action__desc`（"导出全部数据为 JSON 文件，含删除标记，可分享保存。" / "从 JSON 文件恢复数据。校验失败不写入；覆盖前需二次确认。"）——按钮本身已经说明动作，删除。
2. `dm-hint`（"删除标记用于跨设备同步，不会被清除。"）——属于实现细节暴露，删除；「删除标记」这一统计项也一并移除，它对用户无决策价值。
3. `glass-cell desc="默认关闭，P1 可插拔"`——开发者黑话，直接删除 desc。

### B2. 用布局替代文字的具体做法

- **三段式卡片改两段**：`标题 + 按钮`。标题即动作名（导出备份 / 导入备份 / 微信账单），不再配正文。
- **数字前置**：把「N 条账单 / N 个分类 / N 项预算」放页面顶部一行，代替任何"当前数据概况如下"的引导句。
- **分组靠间距与标题**：`--sp-6` 分隔大组，组标题 15px/600，组内 `--card-gap`。层级由留白表达，不加分割线也不加副标题。
- **危险动作靠形态区分**：覆盖类操作按钮用 `--color-expense` 描边，并在按钮上方只留一行 `--fs-caption` 的风险句（这是唯一允许保留的说明类型）。

### B3. 允许保留说明的两种情况（其余一律删）

1. 不可逆后果：覆盖导入、清空。
2. 能力降级：分享不可用、需要先把文件发到聊天。

两种都限一行、`--fs-caption`、`--color-text-3`，不得换行堆叠成段。

### B4. 禁止项

- 禁止新增装饰性 emoji、ⓘ 图标去承载解释；图标只用于分类色块与既有语义。
- 禁止用颜色**单独**表达状态（新增/跳过必须带文字或数字，色盲可读）。
- 禁止在页面 wxss 新增 `#hex`、`rgba()`、写死 `duration`——全部走 token。
- 禁止改动 `theme.wxss` 的既有 token 值。
- 禁止顺手重写 `index` / `stats` / `record-editor` 的版式。这些页面只做一件事：按 B1 判据列出"可删文案清单"交给用户决策，不动代码。

新增单测（`services/__tests__/wechat-import.service.test.ts`），至少覆盖：

1. 带 16 行说明 + 11 列表头的真实结构账单 → 表头定位正确，解析笔数与声明一致。
2. 收入项（转账收款、红包）方向正确，不被记为支出。
3. `¥65.00` → `6500` 分，无浮点误差。
4. 含逗号的引号字段切分正确。
5. 中性交易与全额退款被排除且计数正确。
6. 同一份全量账单连导两次 → 第二次新增 0、跳过 N。
7. 账本已有 1 条旧数据（无单号）后再导全量 → 新增 N-1、跳过 1，同日同额第二笔保留。
8. 表头无法识别时返回空结果且**不写库**。

人工走查（真机或开发者工具）：

- 从聊天文件选一份真实账单 → 预览数字与账单首页声明对得上，对不上要能指出差在哪类。
- 确认后账单列表出现记录，金额为分、日期为 `YYYY-MM-DD`、分类落到预设分类而非全量「其他」。
- 再次导入同一文件 → 提示"这批都已记过"。
- 数据管理页删除文案后，页面在不看任何说明文字的情况下仍能判断三个按钮各自作用。

## 6. 风险与失效点（执行方需在说明里复述一次）

| 风险 | 说明 |
|---|---|
| 取数路径受限 | 小程序只能选聊天里收到的文件，用户必须先发到「文件传输助手」。UI 若不把这一步用布局说清，用户会卡在"选不到文件"。成功率取决于这一步的引导，估 70% 左右。 |
| zip 不可解 | 若用户直接选 zip，只能报「先解压出 csv」。不要尝试引入解压库。 |
| 分类映射不准 | 微信「交易类型」粒度粗（商户消费/转账/红包），首版必然有较多落「其他」。可接受，用「自定义分类关键词」逐步收敛，不追求一次到位。 |
| 去重口径 | 单号缺失时靠计数对齐，属于近似幂等；同一笔被用户手动改过金额后再导，会重复计入。接受此代价，不做模糊匹配。 |
| 文案删减过头 | 删说明后若真机走查发现用户误触覆盖导入，则只在覆盖类操作上补回一行风险句，不得回滚成整段说明。 |
