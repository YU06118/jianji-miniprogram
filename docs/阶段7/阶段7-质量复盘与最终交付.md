## 4 最有价值的三个案例

### 案例 1：P0 墓碑丢失 —— 连续操作才现形
`deleteRecord()` 用 `loadRecords()`（已过滤墓碑）→ 标记 → `saveRecords()` 整体覆盖。单个删除测试全绿，连续删除两条时第一条墓碑消失。修复：新增 `readAllRecords()` 全量读原语，7 个写操作改基于全量。**教训：状态的"读取-过滤-写回"模式必然丢被过滤的数据；复现测试要覆盖连续操作。**

### 案例 2：L2 建议被正确反驳 —— 性能不能牺牲正确性
检查方建议 `pendingUploads` 的 `>=` 改 `>` 以减少冗余上传。修复方反例：时间相等但内容不同时，`>=` 上传本地新版本、`>` 上传 0 条 → 本地版本永远推不到云端，破坏"本地优先"语义。检查方独立复验后认错，保持 `>=` 并锁定回归用例。**教训：以"性能"之名动正确性语义时，必须构造反例双向验证；检查建议不总是真理。**

### 案例 3：Q7 名称锁定 —— 清单型需求要锁具体值
原单测只验 8 项数量、6-2 分布、全 builtIn，把"餐饮"改成"吃饭"照样全绿。补精确名称数组断言后，注入改名立即失败。**教训：固定清单/枚举类需求，单测必须断言具体值逐个相等，并注入一个错误值确认测试会红。**

## 7 下一版本改进建议

1. **写操作统一走全量原语**：把 `readAllXxx` 作为写路径的唯一入口，从架构上杜绝"展示过滤集写回"的数据丢失（P0 根因的根治）。
2. **清单型需求建立"值锁定"规范**：所有固定枚举（预设分类、状态码、支持格式）单测必须断言具体值，并注入验证。
3. **延时导航统一封装**：所有"动画结束后 navigate"的场景封装为带 timer 清理 + 返回拦截的公共方法，避免多退栈。
4. **文档与代码同步检查纳入 CI**：README / 部署说明 / 走查清单中的版本号、路径、口径，用脚本比对代码常量，避免文档漂移（本项目出现过 3 处文档矛盾）。
5. **保留"检查方被反驳"的记录**：这类双向质疑是高价值质量信号，建议沉淀为团队 check list 条目。
