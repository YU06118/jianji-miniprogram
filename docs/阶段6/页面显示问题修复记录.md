# 页面显示问题修复记录（2026-11-26）

> 触发：用户截图反馈两个问题——① 首页"缩放有问题、元素显示不齐全"；② 底部导航栏"能见度不高"。
> 范围：用户确认选 C 档，全部 13 个页面一次做全。

## 二、修复内容

### Fix 1 — glass-card 样式隔离（1 行）

`components/glass-card/index.ts` 加 `options: { styleIsolation: 'apply-shared' }`。
11 处 extClass 用法（先 grep 确认）的页面样式恢复生效，概览卡回到三列布局。

### Fix 2 — 全部 13 页顶部安全区避让

- **新增 `utils/nav.ts`**：`computeNavSafeTop()`——胶囊矩形有效时取 `rect.bottom + 8`（跨端可靠），异常回退 `statusBarHeight + 44`；`getThemeBootstrap()` 统一从 globalData 取 compat + navSafeTop。
- **`app.ts`**：globalData 增加 `navSafeTop`，onLaunch 计算一次；export `AppGlobalData` / `AppOptionWithGlobalData` 类型。
- **`app.wxss`**：`.page-content` 加 `padding-top: var(--nav-safe-top, calc(env(safe-area-inset-top) + var(--sp-4)))`——未绑变量的页面至少有 env() 兜底（iOS/devtools），绑了用 JS 精确值（Android 可靠）。
- **13 页统一注入**：wxml 根节点绑 `compat.rootClass` + `style="--nav-safe-top: {{navSafeTop}}px"`；ts 的 data 增加 `compat`/`navSafeTop`，onLoad 调 `getThemeBootstrap()`。同时修掉地雷②（11 页降级类补绑）。
- **record-editor**：`.editor-header` padding 从 `env(safe-area-inset-top)` 改为 `var(--nav-safe-top, env(...))`（Android env=0 时也有正确避让）。
- **吸顶同步**：`.home-group__header` sticky `top: 0` → `top: var(--nav-safe-top, 0)`（全项目仅此一处 sticky）。

### Fix 3 — tabbar 能见度强化

- **theme.wxss 新增 4 token**：`--color-tab-inactive: #c7c2e0`（未选中，对比约 9:1）、`--color-tab-bg: rgba(13,9,26,.94)`（面板感）、`--color-tab-bg-solid`（降级实色）、`--color-tab-line: rgba(255,255,255,.3)`（发丝线）。
- **custom-tab-bar/index.wxss**：背景/发丝线/未选中色改 token；图标 20px→`--size-icon`(24px)；选中态 = accent 图标 + `--color-text-1` 文字 + 600 字重 + 顶部 20×3px accent 指示条；删除失效的跨界降级规则。
- **custom-tab-bar/index.ts**：`attached()` 读 `globalData.compat.glassSupported`，false 时组件内挂 `tabbar--fallback` 类（实色底、去毛玻璃）——修掉地雷①。

## 四、可复用经验

1. **自定义组件的 extClass 插值在默认 isolated 下无效**——布局类注入必须配 `styleIsolation: 'apply-shared'` 或 `externalClasses`；症状是"页面样式写着却像没写"，典型表现是 flex 容器塌成纵向堆叠。
2. **全局 `navigationStyle: custom` 必须配全局顶部避让**——纯 CSS 的 `env(safe-area-inset-top)` 在 Android 微信常返回 0，行业可靠做法是 JS 取 `getMenuButtonBoundingClientRect().bottom` 后经 CSS 变量注入页面。
3. **组件 wxss 无法用跨界祖先选择器响应页面根类**（`.glass--fallback .tabbar` 永不命中）——降级判定应在组件内读 getApp() 自行挂 class。
4. **深色 UI 的 tabbar 能见度**：未选中与选中色明度接近时选中态形同虚设；细线字符图标（⌂◔○）比实心字形感知更淡，需要更大的字号/加粗/指示条补足。

## 五、边界与待真机验证

- tabbar 图标仍为字符图标，若真机渲染仍过细，后续可换 SVG/图片图标（列入真机走查 B 组观察项）。
- navSafeTop 为 onLaunch 一次计算，分屏/旋转不重算（记账场景可接受）。
- 用户需在开发者工具/真机复验：概览卡三列并排、顶部无重叠、tabbar 选中态清晰。

## 追加：tabbar 二次修复——变量作用域真因（2026-11-26 09:54，用户复验截图）

### 复验结果
概览卡三列并排 ✓、顶部避让 ✓；但 tabbar 与修复前**视觉零变化**（无面板分界、无选中指示条、文字暗淡）。

### 真因
Fix 3 的新 token 从未被解析——**custom-tab-bar 是框架级独立挂载的组件**：
1. 不在页面 `.theme-root` 节点树内（theme.wxss 变量定义在 `page, .theme-root` 选择器上，页面 WXML 根节点带 theme-root 类所以页面内一切正常——截图里概览卡/FAB 颜色全对即为佐证）；
2. 组件不继承 app.wxss，组件 wxss 也未引入 theme.wxss；
3. 组件内没有 `page` 元素可匹配 `page` 选择器。
→ 组件内所有 `var()` 无定义，背景/文字/毛玻璃全部回退初始值（透明/黑）。这同时解释了修复前"看不出选中项"：accent 色从未生效过，所有 tab 文字都是回退黑。

### 判定偏差复盘
首轮把根因判为"设计对比度不足"，排除了"变量不解析"假设——当时依据标准 CSS 行为推理"var() 失败会继承亮白"，但微信 WXSS 对无效 var() 的回退与 custom-tab-bar 的特殊挂载位置使该推理不成立。**证据其实早已指向变量失效**（无面板分界 + 选中态无差异，两个现象用"对比度不足"解释牵强）。教训：多个假设都能解释现象时，优先设计区分性实验（如在 tabbar 写死一个纯色看是否生效），而不是选"看起来最合理"的那个。

### 二次修复
1. `custom-tab-bar/index.wxml`：根节点 class 加 `theme-root`——theme.wxss 的 `.theme-root` 选择器在组件内匹配根节点，变量全部定义进组件作用域。
2. `custom-tab-bar/index.wxss`：顶部 `@import "../theme.wxss";`——组件不继承 app.wxss，须显式引入。
零硬编码（色值仍在 theme.wxss），verify-static 无需改动。

### 验证
`npm run verify:all` EXIT 0（tsc 0 / ESLint 0 / Jest 14 套 127 例 / 静态 7 项全过）。待用户重新编译复验 tabbar。
